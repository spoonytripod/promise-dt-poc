## 1. 목표와 우선순위

최신 자산 관리 기획을 기준으로 예시 데이터를 직접 등록하고 수정할 수 있는 HTML 시제품을 만든다. 기존 `pages/page-asset.html`은 기능 정의 이전에 만든 컨셉 목업이다. 기존 카드나 메뉴를 그대로 확장하기보다 본 문서의 업무 흐름에 맞춰 재작성한다.

본 문서는 이번 개편의 기능 범위를 정리한 기준이다. 사용자의 후속 요청이 있으면 이를 우선한다. 과거 기획 문서의 구현 보류 사항과 이번 합의가 충돌하면, 이번에 포함하기로 결정한 기능은 시제품에 구현하고 실제 DB 반영 필요 사항을 별도로 기록한다. 원본 연구 자료의 계획이나 과거 상태를 현재 구현 완료 사실로 해석하지 않는다.

## 5. 자산 속성과 도메인 규칙

### 5.1 속성 기준

원본 기획의 자산대장 속성은 아래와 같다. 기존 데이터 정의와 일치하는 명칭을 우선하고, 화면에서 선택한 코드로 관련 명칭과 연락처를 조회한다.

| 묶음 | 항목 | 입력과 표시 기준 |
| --- | --- | --- |
| 식별 | 자산번호, 태그번호, 자산명, 영문 자산명 | 자산번호와 국문 및 영문 자산명 필수. 태그가 없는 예비 자산 허용 |
| 상위 자산 | 상위 자산번호, 상위 자산 태그 | 원본 속성에 존재하지만 부속 자산 구현은 후속. 이번 편집 양식에서는 제외하고 향후 확장 항목으로 명시 |
| 분류와 상태 | 설비 유형, 영문 설비 유형, 중요도, 운영 상태 | 설비 유형, 중요도, 운영 상태 필수. 영문 유형은 선택한 분류에서 조회 |
| 제품 | 제조사, 제조사 연락처, 모델명, 제조사 파트번호, 규격과 사양, 제조일자 | 제조사 연락처는 제조사 기준정보에서 조회 |
| 도입 | 취득일자, 설치일자, 내구연한 | 설치일자는 설치 기록과 일치해야 하며 일반 수정으로 이력과 불일치하게 만들지 않음 |
| 관리 | 관리 기관, 관리 부서, 담당자, 담당자 연락처, 비고 | 기관과 부서 및 담당자를 하나의 기준정보 레코드로 선택. 예시는 가상의 정보 사용 |

중요도는 A(고장 시 공정 정지 또는 수질 이탈), B(성능 저하가 있으나 운전 지속 가능), C(단기 영향 없음)로 구분한다. 운영 상태는 가동, 정지, 예비, 폐기를 사용한다.

### 5.2 식별과 설치

- 태그는 기능적 위치이고 자산은 그 위치를 점유하는 실물이다. 내부 연결에는 불변인 `tag_id`와 `asset_id`를 사용한다. 화면에는 태그번호와 자산번호를 표시한다.
- 도면 개정으로 태그번호가 바뀌어도 내부 식별자를 새로 만들지 않는다. 태그 신설과 변경에는 도면 근거를 남긴다.
- 한 태그에는 현재 자산이 최대 하나만 설치된다. 한 자산도 동시에 여러 태그에 설치될 수 없다. 자산이 없는 태그 자체는 정상적인 데이터다.
- 설치와 교체 시 현재 연결과 설치 기간 이력을 함께 갱신한다. 기존 자산에 새 제품 정보를 덮어쓰지 않는다.
- 교체 처리 중 일부만 저장되는 상태를 방지한다. 기간 역전이나 중복 설치 등 잘못된 입력에는 원인을 표시한다.
- 폐기 자산의 재설치와 비활성 태그의 신규 설치는 차단한다. 점유 중인 태그 비활성화에는 먼저 해체 또는 교체 처리가 필요하다.

### 5.3 점검과 정비

- 태그별 점검 계획은 설비 교체 후에도 유지한다. 수행 기록에는 수행 당시의 자산을 연결하여 이전 펌프와 새 펌프의 정비 이력을 구분한다.
- 예비 자산의 자산별 계획과 태그별 계획을 구분한다. 설치와 교체를 이유로 두 계획을 자동 병합하지 않는다.
- 기본 주기는 달력 기준이다. 완료 처리 시 다음 예정일을 제시하고 사용자가 확인하거나 조정한 값을 저장한다. 운전시간 기반 자동 산정은 후속이다.
- 운영 상태와 점검 상태를 별도로 계산하고 표시한다. 가동 중인 설비도 점검 기한 초과일 수 있다.
- 실제 정비 기록과 자산 정보 수정 기록은 서로 다른 이력이다. 정비 일자를 바꾸는 경우에도 정보 변경 이력을 남긴다.

### 5.4 문서와 엑셀

- 파일 원본과 연결 정보를 분리한다. 공통 P&ID를 여러 대상에 연결해도 원본은 한 번만 저장한다.
- 연결 해제와 파일 삭제를 구분한다. 다른 대상에서 참조 중인 파일은 삭제하지 않는다. 내장 PDF, 이미지, DWG 미리보기는 만들지 않는다.
- 엑셀 형식은 `.xlsx`다. 필수값, 코드, 중복 자산번호, 존재하지 않는 태그와 점유 충돌을 검사한다.
- 신규 자산 일괄 등록은 전체 검증 후 저장한다. 오류가 있으면 행과 항목별 사유를 보여주고 아무 행도 저장하지 않는다. 등록 완료 전 마지막으로 현재 데이터와 충돌 여부를 확인한다.
- 제조사 연락처처럼 다른 기준정보에서 조회하는 값은 중복 저장하지 않는다. 원본 양식의 상위 자산 항목이 입력되면 미지원 범위임을 알려야 하며 조용히 무시하지 않는다.

## 6. 구현 구조와 저장 방식

### 6.1 시제품 데이터

기존 `asset_info`, `tag_info`, `process_info`, `asset_class`, `mfr_info`, `mgr_info`의 개념을 따른다. 실제 DB 적용 여부와 별개로 예시 데이터를 준비한다.

시제품에는 설치 기간 이력, 점검 계획, 점검 및 정비 수행 기록, 문서 원본과 연결, 정보 변경 이력에 해당하는 데이터가 추가로 필요하다. 이를 기존 운영 DB에 이미 존재하는 테이블로 설명하지 않는다. 구현 명세에 기존 속성의 대응 관계와 향후 DB 확장 필요 항목을 구분해 기록한다.

데이터와 첨부파일 Blob은 IndexedDB에 보관한다. 저장소 버전과 초기화 여부를 관리하고 최초 실행 때만 예시 데이터를 넣는다. 새로고침이나 페이지 이동 때 다시 초기화하지 않는다. 화면 처리와 저장 처리를 분리하여 웹과 통합 데모가 같은 업무 로직을 사용하도록 한다.

### 6.2 웹과 단일 HTML

- 웹 페이지에서는 해당 사이트의 저장 서비스를 사용한다.
- 단일 HTML 생성기는 페이지를 iframe으로 묶는다. 단일 HTML 래퍼에 저장 서비스를 두고 자산 관리 iframe에서 호출하도록 연결한다. 파일로 열었을 때의 저장 접근과 재실행 복원은 가장 먼저 검증한다.
- 메시지로 연결하는 경우 요청 식별자와 성공 및 실패 응답을 구분하고, 요청이 해당 자산 관리 iframe에서 왔는지 확인한다. 기존 메뉴 이동 메시지와 충돌하지 않게 한다.
- 저장 실패나 용량 초과를 저장 성공으로 표시하지 않는다. 메모리 보관으로 조용히 대체하지 말고 사용자가 상태를 알 수 있게 한다.
- 웹과 로컬 단일 HTML의 저장 데이터는 각각 독립적이며 자동 동기화하지 않는다. 브라우저 데이터 삭제 시 보관 내용이 사라지는 특성을 사용 안내에 명시한다.
- 단일 HTML에서는 자산 관리에 필요한 코드, 엑셀 라이브러리와 초기 자료를 함께 포함한다. 생성된 `demo_standalone.html`을 직접 수정하지 않는다.

파일 실행 환경의 IndexedDB 접근이 브라우저 정책으로 차단되는 경우에는 데이터 유지 조건을 몰래 낮추지 않는다. 재현 조건을 기록하고 해결 또는 사용자와 제공 방식 조정이 필요한 미완료 사항으로 보고한다.

### 6.3 엑셀 라이브러리

SheetJS CE 0.20.3의 브라우저 배포본을 저장소에 포함하고 라이선스 정보를 보존한다. 실행 시 외부 CDN에 의존하지 않고 단일 HTML에도 내장한다. 출처: [SheetJS 공식 설치 안내](https://docs.sheetjs.com/docs/getting-started/installation/standalone/).

## 7. 구현 순서

1. 현재 브랜치와 작업 변경 사항을 확인하고 관련 지침, 디자인 가이드, 기존 페이지와 번들 생성기를 읽는다.
2. 본 문서 기준으로 기능별 화면, 입력값, 처리 결과와 데이터 대응 관계를 구현 명세에 정리한다. 원본 연구 문서의 구현 보류와 이번 시제품 범위의 차이를 명시한다.
3. 웹과 단일 HTML에서 데이터 및 파일 저장, 새로고침, 브라우저 재실행 복원을 먼저 검증한다. 이 단계가 해결되지 않은 상태에서 나머지 화면을 완성했다고 보고하지 않는다.
4. 공통 데이터 처리와 자산대장, 탐색, 상세, 등록과 수정 기능을 구현한다.
5. 설치, 해체, 교체와 폐기 기능을 연결하고 이력 정합성을 검증한다.
6. 점검 계획과 수행 기록, 문서 관리, 기준정보와 변경 이력을 구현한다.
7. 엑셀 처리와 예시 데이터 초기화를 추가하고 공통 메뉴 표시명을 맞춘다.
8. 단일 HTML 생성기를 갱신한 뒤 전체 시나리오를 웹과 단일 HTML에서 반복 검증한다.
9. 실행 방법, 검증 결과와 남은 제약을 문서로 제공한다. 실제 서비스 반영이나 원격 배포는 별도 요청 없이 수행하지 않는다.

## 8. 검증과 완료 기준

기본 검증 환경은 Windows의 Chrome과 Edge다. 시제품 데이터임을 분명히 표시하고 실제 운영 기록으로 오인할 내용을 만들지 않는다.

| 검증 사례 | 기대 결과 |
| --- | --- |

| 미설치 자산과 빈 태그 | 예비 자산이 누락되지 않고 자산이 없는 태그도 정상 조회됨 |

| 폐기 처리 | 현재 설치 관계가 종료되며 과거 정보와 이력이 유지됨 |
| 점검 완료 | 수행 결과, 당시 자산과 다음 예정일을 확인할 수 있고 기한 초과 표시가 갱신됨 |
| 운영 상태와 점검 상태 | 가동 중인 자산의 기한 초과 등 두 상태를 동시에 정확히 표시함 |
| 엑셀 오류 | 오류 행과 항목을 표시하며 부분 저장이나 기존 자산 덮어쓰기가 발생하지 않음 |
| 엑셀 정상 등록과 내보내기 | 신규 자산이 일괄 저장되고 내보내기에 검색 결과 전체가 포함됨 |
| 공통 문서 | 여러 대상에서 같은 파일 조회, 연결 해제와 삭제 구분, 원본과 동일한 파일 다운로드 |
| 비활성 기준정보 | 기존 자산의 명칭과 과거 기록은 유지되고 신규 선택에서는 제외됨 |
| 정보 변경 | 이전 값, 변경 값, 시각과 작업자명을 조회할 수 있음 |
| 브라우저 재실행 | 데이터와 첨부파일이 유지되며 예시 데이터가 중복 생성되지 않음 |
| 저장 실패 | 성공 메시지가 표시되지 않으며 원인을 알 수 있고 기존 데이터가 보존됨 |
| 초기화 | 확인 후 자산 관리 시제품 데이터만 초기화됨 |
| 단일 HTML | 서버 없이 열어 자산 관리의 주요 업무, 엑셀과 파일 다운로드, 저장과 복원이 동작함 |
| 회귀 검증 | 기존 상단 메뉴 이동과 다른 페이지가 유지되고 실행 오류가 없음 |
| 화면 사용성 | 긴 목록, 긴 문서명, 비어 있는 결과와 상세 화면에서도 버튼과 입력란에 접근 가능 |

업무 규칙과 저장 무결성은 자동 검증을 우선하고, 파일 다운로드와 브라우저 재실행, 단일 HTML 및 화면 사용성은 실제 브라우저 검증을 병행한다. 결과를 기능 ID와 연결해 기록한다.

저장소 루트에서 웹 확인용으로 `python -m http.server 8000`을 사용할 수 있다. 통합 데모 생성은 기존 명령 `uv run scripts/create_standalone.py`를 사용한다. `uv`가 없으면 스크립트 의존성을 확인한 뒤 `python scripts/create_standalone.py`로 실행한다. 생성 성공만으로 브라우저 동작 검증을 대신하지 않는다.
